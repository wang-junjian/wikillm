# 什么是 Harness 工程：2026 定义性指南

**Harness 工程**是设计并维护控制系统的学科，这套控制系统负责治理 AI 智能体如何感知环境、选择行动并验证结果。它既不同于提示词工程，也不同于模型选型：Harness 是包裹模型的一切——引导智能体的 guides、验证其行为的 sensors，以及供给推理所需信息的数据上下文管道。

本文编译自 Atlan 于 2026 年发布的定义性指南。与多数将 Harness 工程视为纯软件问题的文献不同，该指南的核心立场是：**Harness 工程在很大程度上是一个被伪装起来的数据问题**。

## 定义框架：Agent = Model + Harness

2026 年初，OpenAI 工程师 Ryan Lopopolo 发表了一篇关于内部智能体基础设施的文章，描述一支小团队如何以智能体优先的方式在长期演进的代码库上运行 Codex：推理模型自始至终未变，真正拉动吞吐量的是围绕模型的 Harness。数月之内，Terraform 与 Ghostty 的创造者 Mitchell Hashimoto 将其核心洞见提炼为一个公式：

> **Agent = Model + Harness（智能体 = 模型 + Harness）**

Martin Fowler 通过 Thoughtworks 工程师 Birgitta Böckeler 发表的严谨指南扩展了该框架，提出 guides-and-sensors 分类法，这套词汇随后成为业界讨论 Harness 组件的标准语言（详见 [[Harness-Engineering-for-Coding-Agent-Users|面向编码智能体用户的 Harness 工程]]）。该术语迅速流行，因为它给了团队一样提示词工程从未提供过的东西：为「模型之外的一切」命名。

该公式包含三层主张：

1. **模型本身不构成智能体**。智能体是模型加上治理它的控制系统。
2. **模型是商品**。无论选择哪个前沿模型，在 Harness 层面它都是可互换的推理引擎，更换模型无需重写 Harness。
3. **Harness 是竞争护城河**。它编码了业务规则、数据上下文、安全约束与验证逻辑，这些资产在切换模型时全部保留。

两个业界案例印证了以 Harness 为主要工程投入的效果：

- **OpenClaw**——Peter Steinberger 的智能体系统每月落地 6,600+ 次提交，5 到 10 个智能体并行运作，全程无模型微调，一切由 Harness 治理。
- **Stripe Minions**——Stripe 内部智能体基础设施每周合并 1,000+ 个 Pull Request，评审前无人工介入。模型是标准件，Harness 才是工程成就。

## 核心组件：Guides 与 Sensors

Harness 组件按控制系统理论分为两类：**guides 是前馈控制**，在智能体行动之前约束并引导它；**sensors 是反馈控制**，在智能体行动之后观察并验证，在错误级联至下游系统之前将其捕获。二者共同构成把原始语言模型转化为生产级智能体的控制系统。

### Guides：前馈控制

构建良好的 guide 层编码了足够多的结构，使智能体几乎无需临场发挥。核心组件包括：

- **系统提示词**——定义人格、任务范围与输出格式的基础指令集
- **AGENTS.md 文件**——代码库级文档，告知智能体可触碰哪些文件、遵循哪些约定、可用哪些工具
- **约束文件**——显式规则集，界定智能体绝不可为之事以及需要人工批准之事
- **上下文管道**——运行时喂给智能体的数据：schema 定义、表元数据、血缘、认证状态

OpenAI 的案例中，guides 编码了语言约定、测试要求与代码评审标准；一致且可评审的代码出自精心设计的 guides，而非更强的模型。

### Sensors：反馈控制

构建良好的 sensor 层在故障抵达生产之前将其拦截。核心组件包括：

- **Evals**——对照 ground truth 为智能体结果打分的自动化测试套件，是检测能力随时间退化的关键手段
- **验证循环**——实时检查，在违反约束的结果被提交之前予以标记
- **输出解析器**——将 LLM 文本转化为带类型、可验证数据的结构化抽取器
- **漂移检测器**——捕获智能体行为意外变化的传感器，其触发往往源于底层数据的变化而非模型行为的变化

## 为什么 Harness 工程在 2026 年至关重要

**88% 的 AI 智能体项目从未进入生产**（DigitalApplied, 2026），且该数字并未随模型能力提升而改善——瓶颈不在模型，而在生产级 Harness 的缺失。2026 年 4 月的 AI Engineer World's Fair 上，三位相互独立的演讲者不约而同地将「智能体 Harness」与「上下文工程」列为头号优先级，反映出行业注意力在两年模型能力竞赛之后的转向。

多方数据源的失败证据高度一致：

- **95% 的企业 AI 试点未能交付可衡量的 ROI**，根因被认定为上下文缺口而非模型局限（MIT, 2025）
- 仅 **12% 的组织拥有足以支撑 AI 的数据质量**（Precisely, 2025）
- Gartner 预测，到 2027 年底将有超过 **40% 的 agentic AI 项目被取消**，原因是成本攀升、商业价值不明或风险控制不足

上述每一种失败模式本质上都是 Harness 问题——更确切地说，是 Harness 喂给智能体的数据的问题。

## 隐藏层：Harness 为何失败在数据层

最常见的 Harness 失败并非架构问题，而是数据问题。**27% 的 AI 智能体项目失败由数据质量失效引起**（DigitalApplied, 2026），是仅次于范围蔓延的第二大失败原因。工程团队构建了出色的 guide 层、撰写了详尽的 AGENTS.md、部署了稳健的验证循环，智能体在生产中依然给出错误答案——根因不在 Harness 架构，而在 Harness 喂给智能体的数据。

数据层失败在实践中的典型形态：

- Harness 向智能体提供 `revenue_q4` 列，但底层表在上次迁移中被重命名，旧列如今只返回空值
- 智能体查询的 schema 自 guides 撰写以来已经发生漂移；它依照一份与现实不再匹配的数据心智模型运作
- 血缘过期：智能体认为表 A 供给表 B，但管道三周前已变更，依赖关系不复存在
- 质量检查通过仅仅因为数据存在，但认证已失效，数值不再可信

Atlan 的调研显示，**39% 的数据工程师将 schema 漂移列为头号 AI 风险**。Schema 漂移是最常见的隐性 Harness 失败：架构完好无损，内部的数据却已改变。这正是「Harness 工程作为软件关切」与「Harness 工程作为数据关切」的分野——所有高排名文献都把它当作软件工程问题，没有一篇追问过 Harness 所依赖的数据悄然变化时会发生什么。

## 以受治理的数据层支撑 Harness 工程

受治理的数据上下文层负责解决那 80% 源自数据源的 Harness 失败。多数 Harness 工程工具只覆盖剩下 20%：架构、编排框架、eval 套件，却不触及失败真正发生的位置——数据上下文层。当智能体查询 `certified_revenue` 而该列已在上次 schema 迁移中被废弃时，再好的 Harness 架构也无法阻止错误结果。

此类数据层的工程形态包括：

- **认证过的列定义**——智能体获取的每个字段都带有可信状态标记
- **活跃血缘**——展示哪些表供给哪些下游结果，随管道变更实时更新
- **质量信号**——标记不应被信任的数据资产
- **Schema 变更告警**——在上下文漂移抵达智能体之前将其浮出水面

落地路径上，企业数据图谱（Enterprise Data Graph）承担底层支撑：一张覆盖全部数据资产及其关系的实时可查询地图，通过 MCP 服务器以编程方式投递上下文——Harness 查询某数据资产的当前状态，即可收到认证状态、最近验证过的血缘以及活跃的质量告警。采用受治理数据上下文层的组织报告了 **SQL 准确率提升 38%** 的成绩：同一模型、同一 Harness 架构，差异只在治理更好的数据。

## 结论：Harness 工程是伪装之下的数据问题

Harness 工程是把语言模型转化为生产级智能体的学科。guides、sensors、约束文件这套词汇是必要但不充分的：可靠的智能体需要受治理的数据层，而不仅仅是架构良好的 Harness。对数据层的投入不足，正是多数团队与那 27% 数据质量失败率正面相撞的原因。
