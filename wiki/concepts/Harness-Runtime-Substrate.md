# AI Harness 工程：基础模型软件智能体的运行时基座

这篇论文（香港浸会大学 Hailin Zhong 与北京师范大学珠海校区 Shengxin Zhu）提出了一个立场鲜明的观点：自主软件工程能力的短板不在模型本身，而在模型周围的**运行时基座（runtime substrate）**——即 Harness。论文把 Harness 正式定义为一个独立的研究对象，给出十一项组件职责、一个 H0–H3 受控可见性阶梯，以及一套基于轨迹（trace）的评估协议，把每一次智能体运行转化为可审计的" episode 包"。

> **核心论点**：自主软件工程能力是 *模型–Harness–环境系统* 的涌现属性，而非模型的单独属性。核心问题应该从"模型能否打出一个补丁"转变为"模型–Harness–环境系统能否打出一个**可验证、可归因、可维护**的变更"。

形式化地，系统能力写作：

$$
C_{\text{system}} = F\bigl(C_{\text{model}},\,C_{\text{harness}},\,C_{\text{environment}},\,T\bigr)
$$

其中 $C_{\text{model}}$ 是基础模型的潜在能力，$C_{\text{environment}}$ 是软件环境暴露的内容，$C_{\text{harness}}$ 是居中调节的运行时基座，$T$ 是任务分布。Harness 决定了模型的潜在能力能否转化为**可审计的**软件工程行为。这一视角与 [[What-Is-Harness-Engineering|Harness 工程的定义]]、[[From-Weights-to-Context-to-Harness|从权重到 Context 再到 Harness]] 的演进脉络一脉相承。

![模型-Harness-环境系统](../assets/AI%20Harness%20Engineering%20A%20Runtime%20Substrate%20for%20Foundation-Model%20Software%20Agents-fef6205f48cdbd39e7dd1e19a8f706c5d50fe390.svg)

**图 1**：模型–Harness–环境系统。基础模型提供潜在的推理与编码能力；软件环境提供仓库、测试、工具、日志与构建能力；AI Harness 居中调节 Context、动作、反馈与验证证据。

## 自主鸿沟与失败分类

### 编码能力 ≠ 软件工程能力

论文严格区分两个概念：能写出正确局部代码片段的是**编码能力**；而**软件工程能力**是一个有状态的过程，涉及仓库导航、Context 选择、工具使用、测试执行、失败解读、验证、文档与维护。局部基准上的高分被误读为完整软件工程能力，是典型的归因错误——现实中模型从不单独行动，它的每一步都被运行时结构所调节。

**自主鸿沟（autonomy gap）**定义为：模型的表面局部编码能力，与完整系统在没有"替代运行时"的人类帮助下完成软件任务的能力之间的差距。它不是单一失败模式，而是一族失败：检查错误的文件、误读测试输出、在错误的架构层打补丁、只验证新改动而忘记回归、没有留下证据就宣布完成。每一种都对应一项缺失的 Harness 职责。

### 人类干预作为运行时信号

传统智能体评估把人类帮助视为噪声或直接禁止，本文反其道而行：把人类干预当作**诊断信号**。人类告诉智能体该看哪个文件，说明 Context 管理器缺失；人类替智能体解读测试失败，说明可观测性或失败归因支持缺失；人类亲自验证最终行为，说明验证协议缺失。论文将此类干预命名为**缺失 Harness 的人类干预**，并定义其比率：

$$
\text{M-HIR} = \frac{\text{缺失 Harness 的干预次数}}{\text{总 episode 数}}
$$

能降低 M-HIR 的 Harness，就是补齐了原本需要人类提供的运行时支持。

### 八类失败分类法

| 失败类型 | 含义 |
|---------|------|
| $F_{\text{context}}$ | 缺少或误用相关 Context |
| $F_{\text{tool}}$ | 工具缺失、不稳定或被误用 |
| $F_{\text{feedback}}$ | 反馈不可用或无法解读 |
| $F_{\text{verify}}$ | 无法证明任务需求已满足 |
| $F_{\text{recovery}}$ | 无法从失败中恢复 |
| $F_{\text{entropy}}$ | 引入维护负担（残留、腐化） |
| $F_{\text{model}}$ | Harness 与环境充足时仍出现的模型推理/编码失败 |
| $F_{\text{unknown}}$ | 无法确信归因的失败 |

这套分类法让评估能回答 pass/fail 无法回答的问题：智能体失败时，**缺的是哪一类运行时支持？**

## Harness 的定义与设计原则

**定义**：AI Harness 是包围基础模型软件智能体的运行时基座，管理 Context、工具、项目记忆、任务状态、可观测性、失败归因、验证、权限与维护状态，使模型的潜在编码能力变成可审计的软件工程行为。

四点推论：

1. Harness **外在于模型**——影响模型行为但不是模型本身；
2. Harness 是**任务运行时基础设施**——管辖智能体如何观察项目、采取行动、接收反馈、确立完成；
3. Harness 是**可评估的**——组件可以暴露、隐藏、消融、追踪、对比；
4. Harness **生产证据**——为何选择这些文件、用了哪些工具、失败如何归因、哪些需求被验证、是否需要人类介入、引入了多少维护负担。

### 五条设计原则

- **P1 显式运行时资源**：Context、工具能力、项目记忆、验证证据、人类注意力、权限边界、维护状态都被暴露和命名，而非隐式存在；
- **P2 可追踪的调节**：记录智能体如何选择 Context、调用工具、尝试验证、从失败恢复、引发干预；
- **P3 需求级验证**：任务完成绑定到证据（确定性检查、定向测试、回归、lint、补丁审查），而非自然语言断言；
- **P4 先归因后恢复**：失败的观察先生成分类诊断，智能体才能再次编辑；
- **P5 维护与熵意识**：记录智能体引入的维护负担（过期文档、依赖churn、生成残留、测试弱化、边界违反）。

### 十一项组件职责

| 组件 | 运行时契约 | 缺失时的失败 | 证据产物 |
|------|-----------|-------------|---------|
| 任务接口 | 呈现目标、需求、约束、成功标准 | 目标欠规约；做错对象 | 任务记录 |
| Context 管理器 | 选择并暴露任务相关的项目内容 | 查错文件；遗漏约束 | Context 轨迹 |
| 工具注册表 | 声明可用工具与允许的命令 | 调用失败；危险命令；反复超时 | 工具轨迹 |
| 项目记忆 | 提供智能体可读的架构、测试、已知失败知识 | 重复重新发现；错层修复 | 记忆引用 |
| 任务状态 | 维护假设、已查文件、待解问题、下一步 | 漂移；重复劳动；不连贯 | 任务状态文件 |
| 可观测层 | 暴露日志、轨迹、输出、运行时错误 | 成功不可验证；失败不可诊断 | 观察日志 |
| 失败归因 | 分离观察、预期行为、诊断 | 失败后随机打补丁 | 归因日志 |
| 验证协议 | 把任务需求映射到确定性证据 | 未验证的成功；虚假信心 | 验证轨迹 |
| 权限边界 | 限制危险动作；暴露审批闸门 | 不安全、无效的 episode | 权限记录 |
| 熵审计器 | 检测智能体引入的维护负担 | 过期文档；依赖churn；残留 | 熵审计 |
| 干预记录器 | 记录人类协助及其可避免性 | 隐形的人类脚手架 | 干预日志 |

### 资源管理视角

论文借用操作系统的类比（仅作透镜，不主张机制迁移）：传统 OS 管理 CPU、内存、文件、进程；开发 Harness 管理的是**Context 预算、工具预算、验证证据、项目记忆、任务状态、人类注意力、权限边界、失败信号、熵预算、测试时算力**这十类资源。类比的价值仅在于指出：要让智能体行为连贯、可验证、可维护，必须管理什么。

### 与相邻概念的定位区分

Harness **不是** Prompt（Prompt 塑造单次调用，Harness 管辖整个 episode）；**不是**智能体框架（框架提供组合基础设施，Harness 是暴露给软件智能体的运行时支持配置）；**不是**智能体–计算机接口（ACI 只是 Harness 的一个组件）；**不是**智能体操作系统（agent OS 面向通用调度，Harness 面向软件工程专用基座）；**不是**评估 Harness（评估 Harness 测量行为，开发 Harness 塑造行为）；**也不是** DevOps/平台工程。Harness 可以用上述一切来搭建，但研究对象是"暴露给智能体的运行时支持配置及其证据"。更多辨析参见 [[What-Is-an-AI-Agent-Harness|什么是 AI 智能体 Harness]] 与 [[Anatomy-of-an-Agent-Harness|智能体 Harness 剖析]]。

## H0–H3 受控 Harness 阶梯

为了让 Harness 的贡献与模型的贡献在经验上可分离，论文提出四级阶梯——固定任务、仓库与模型，逐级暴露运行时支持，构成一个受控消融装置。

![H0–H3 Harness 阶梯](../assets/AI%20Harness%20Engineering%20A%20Runtime%20Substrate%20for%20Foundation-Model%20Software%20Agents-30d28a46ffa63e6d5da6473d4be1b6c28d209f58.svg)

- **H0（最小基线）**：只有任务描述和仓库文件。无工具注册表、无项目记忆、无验证协议。是所有级别的对照点。
- **H1（工具 Harness）**：H0 + 工具注册表、测试命令注册表、工具使用协议。动作面变得显式、可追踪，但不提供项目知识或验证纪律。
- **H2（Context–记忆 Harness）**：H1 + 智能体可读的项目记忆（架构、测试约定、已知失败）、任务状态文件、Context 选择协议。
- **H3（可观测–验证 Harness）**：H2 + 确定性行为检查注册表、缺陷复现协议、失败归因协议、验证协议、验证报告模板。把"完成"从断言变成证据对象。

阶梯满足五条设计要求：**R1** 受控可见性（每级只见本级及以下产物）；**R2** 同任务、同仓库、同初始状态；**R3** 运行时支持的使用被记录；**R4** 无隐藏评估者泄漏（期望文件与修复对智能体不可见）；**R5** 结果可比性（所有级别在同一结局分类法下裁决）。可见性单调递增：H0 只见任务描述与仓库文件；H1 增加三件工具产物；H2 增加六件记忆/状态产物；H3 增加五件验证产物；隐藏评估者笔记在任何级别都不可见。

## 基于轨迹的评估协议

阶梯定义智能体能看见什么；评估协议定义每次运行如何被记录、验证、审计与分类。原则：**评估不仅要看是否打出了补丁，更要看系统是否给出了"需求已满足"的可审计证据**。

### Episode 与 Episode 包

一个 *episode* 是模型–Harness–环境系统对指定任务的一次完整尝试，由 episode 标识、模型身份、Harness 级别、仓库、初始 commit、任务规约、可见产物、允许工具、干预策略、验证程序与结局规则共同定义。评估单位是 episode，而非单次模型响应。

每个 episode 产出一个 **episode 包**：八类轨迹 + 补丁 + 验证报告 + 最终报告 + 结局记录。

![评估流水线](../assets/AI%20Harness%20Engineering%20A%20Runtime%20Substrate%20for%20Foundation-Model%20Software%20Agents-297ca5014611609399dbee11e2196b1ad7bc8886.svg)

| 轨迹 | 捕获的运行时资源 | 对应失败类型 |
|------|----------------|-------------|
| action trace | 全部（操作序列） | 整体 episode 连贯性 |
| tool trace | 工具预算；测试时算力 | $F_{\text{tool}}$ |
| context trace | Context 预算；项目记忆 | $F_{\text{context}}$ |
| verification trace | 验证证据 | $F_{\text{verify}}$ |
| failure-attribution log | 失败信号 | $F_{\text{verify}}$, $F_{\text{model}}$ |
| intervention log | 人类注意力 | 全部（诊断信号） |
| entropy audit | 熵预算 | $F_{\text{entropy}}$ |
| outcome record | 最终分类 | 整体裁决 |

所有轨迹以 JSONL 行结构记录，各自带紧凑 schema（如工具轨迹记录命令、退出码、时长、超时状态、失败类型与是否恢复；熵审计按代码/文档/依赖/测试/文件残留/架构/工作流分类并打 0–3 严重度）。

### 五标签结局分类法

| 结局标签 | 含义 |
|---------|------|
| autonomous_verified_success | 需求满足且证据充分，无缺失 Harness 的人类干预 |
| assisted_verified_success | 补丁正确，但关键进展或验证依赖人类协助 |
| unverified_success | 补丁看似正确（评估侧检查通过），但智能体自己没有按协议给出充分证据 |
| failed | 需求行为失败、补丁破坏测试、或无可用补丁 |
| unsafe_invalid | 弱化测试、无关的破坏性编辑、绕过任务 |

这套分类把**任务行为**与**证据质量**分离：补丁可以正确但未验证，失败的补丁也可以有诊断价值。

### 指标族

协议支持一组过程级指标：**AVSR**（自主验证成功率）、**M-HIR**（缺失 Harness 人类干预率）、验证自主度、Context 轨迹有意义度、工具恢复率、失败归因完整度、熵增量。这些都是群体层面的量，在指定的（模型, Harness, 任务, 仓库）单元格上汇总。

## 示例案例：repoA-T1 受控验证任务

论文在一个刻意做小的任务上实例化整个框架（目的在于可检视性，而非群体性能对比）。仓库 repoA 是一个小型 Node.js 登录应用，带一个受控缺陷：登录流程不把空密码拒绝为校验错误，空密码会进入凭据匹配并报告 `Invalid credentials.`。任务要求空密码返回含 `Password is required.` 的校验错误，同时保持既有行为。

**五条需求**：(i) 空密码给出含 "Password is required." 的校验错误；(ii) 有效凭据（alice / correct-password）仍能登录；(iii) 无效非空凭据仍返回 "Invalid credentials."；(iv) 有测试覆盖空密码行为；(v) 既有测试继续通过，或显式记录回归不稳定。

**三个确定性行为探针**：空密码探针、有效登录探针、无效非空凭据探针，各自直接调用登录控制器并期望特定子串。它们在 H3 对智能体可见（作为 Harness 产物），在所有级别同时作为评估侧裁决检查。

**结果（每级一次执行）**：

| 级别 | 最终结局 | 特征性证据 |
|------|---------|-----------|
| H0 | autonomous_verified_success | 补丁；评估侧确定性检查通过；完整回归成功 |
| H1 | unverified_success | 补丁；工具轨迹；定向登录测试；lint；完整回归记录超时 |
| H2 | unverified_success | H1 证据 + 项目记忆的 Context 轨迹；更新的任务状态 |
| H3 | autonomous_verified_success | H2 证据 + 缺陷复现日志；失败归因日志；确定性需求检查；结构化验证报告 |

四级都打出了可用补丁，区分度全在**证据结构**上。H3 把完成绑定到五步纪律：

![H3 验证工作流](../assets/AI%20Harness%20Engineering%20A%20Runtime%20Substrate%20for%20Foundation-Model%20Software%20Agents-71a41e2e478d4b57cc4541c43ad7cef4549a5cd7.svg)

```mermaid
flowchart LR
    A[复现缺陷] --> B[失败归因分类]
    B --> C[针对归因层的定向修复]
    C --> D[验证需求行为与保持行为]
    D --> E[报告证据与局限]
    D -.诊断错误时回退.-> B
```

案例揭示三点：其一，**证据质量随 Harness 级别系统性变化**——工具轨迹从 H1 起出现，Context 轨迹从 H2 起出现，复现日志/归因日志/确定性检查/验证报告只在 H3 出现；其二，**工具不稳定是运行时问题而非杂讯**——H1–H3 都记录了完整回归超时，协议将其显式呈现而非隐藏；其三，**验证可以是 Harness 的职责**——低级别把完成当断言，H3 把完成绑定为需求关联的证据，这正是"补丁"与"可验证变更"的区别。

## 讨论、局限与展望

**五点含义**：(1) 验证是一种运行时能力，放进 Harness 内部可减少对人类审查的依赖；(2) 项目记忆只有在使用被追踪时才可审计——Context 轨迹把记忆从隐形的 Prompt 配料变成可分析的运行时资源（与 [[Memory-Systems|记忆系统]] 的实践相呼应）；(3) 失败归因把诊断与动作分离，避免"幸运修复"与随机补丁；(4) 工具稳定性是 Harness 问题，确定性检查/定向测试/完整回归/lint 的分层记录使其可分析；(5) 熵是自主工程的一部分——残留代码、过期文档、弱化测试不破坏当前任务但长期腐化项目。

**方法论上的诚实声明**：repoA-T1 案例每级只执行一次，用于展示阶梯与协议的可操作性，不支持群体层面的性能结论；AVSR、M-HIR 等指标需要多任务、多模型设计才能获得统计估计。这是框架论文而非基准论文。

**六个延伸方向**：多任务评估（不同任务类别压力测试不同 Harness 组件）；多模型评估（模型 × Harness 级别 × 任务的析因设计）；定量指标（带置信区间的假设检验）；长程评估（同一仓库上的 episode 序列，熵累积与记忆老化）；AI 原生仓库设计（仓库该暴露什么给智能体，而非该为人类放什么）；面向智能体优先开发的运行时系统（专用的"操作系统"，管理 Context、工具、记忆、验证、权限、失败恢复、人类监督、熵、成本与风险）。这与 [[Harness-Heavy-Lifting|Harness 能承担多少繁重工作]] 和 [[Importance-of-Agent-Harness|智能体 Harness 的重要性]] 的实践观察形成互证，也为 [[OpenAI-Codex-Harness-Engineering|OpenAI Codex 的 Harness 工程]] 这类工业报告提供了研究化框架。
