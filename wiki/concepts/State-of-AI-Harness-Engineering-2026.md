# AI Harness 工程行业现状 2026

关于 [[Harness-Engineering|Harness 工程]]——即为智能体构建工具、上下文、记忆与控制循环以使其可靠的学科——讨论很多，但从业者究竟在做什么、效果如何？marmelab 的 François Zaninotto 于 2026 年 9 月发布了一项大规模实证研究：**审计 246 个开源仓库、通读 57 篇出版物**，范围限定在软件开发与编码智能体领域的 Harness，试图回答这门年轻学科的主要趋势、最佳实践与可落地的经验。

一个数字足以说明研究动机：有人将**同一模型**在 8 种不同 Harness 下跑同一组 25 个任务（同一供应商、同一工具集），成功率从 **68% 提升到 88%**。模型没有变，Harness 决定了 20 个百分点的差距——这也是整个语料中唯一被严格测量过的量化证据。

> **利益披露**：marmelab 自己也构建 Harness，其开源产品 Atomic CRM 带有成熟的 Harness，让非开发者通过受监督的智能体流水线修改软件。Atomic CRM 恰好是研究筛出的 11 个标杆仓库之一，读者应带着这一前提理解作者立场。

## 研究方法与样本

### 仓库审计

作者选取了自称 Harness 的开源仓库，以及内部包含 Harness 的大型流行仓库，共 **246 个**，逐一克隆以获取真实首次提交日期、最近活跃度与 `.claude/` 目录下版本化的文件数。

为对冲「自称 Harness 的仓库是有偏样本」的缺陷，作者做了对照实验：克隆 **145 个与 AI 无关的大型开源项目**（Symfony、Rails、Django、React、Kubernetes、Rust、Spring、Odoo 等），用同样方式检查。结果 **26%（38 个）拥有非空 `.claude/` 目录**；54 个完全没有任何智能体配置——包括 symfony、laravel、vuejs/core、golang/go、ruby/ruby、spring-boot、flask、fastapi、tailwindcss、express、nestjs、tokio、redis、postgres、curl、terraform、odoo。结论：**开源世界已经接受了「为智能体写文档」，但还没有开始「约束智能体」**。

### 标杆筛选：从 246 到 11

作者随后寻找「会自我检验的 Harness」。初筛剩 97 个仓库（246 个主样本与 145 个对照中 Harness 文件数 ≥ 3 者，加上以插件形式分发的知名 Harness），再执行四道淘汰：

1. 不测试自己 Harness 的淘汰
2. 每个 Harness 文件的提交数低于 0.5 的淘汰（迭代过滤）
3. 单一作者的淘汰
4. Harness 存活不足 60 天或已休眠 90 天的淘汰

迭代过滤比看上去更重要：`parcadei/Continuous-Claude-v3` 携带 **718 个 Harness 文件**（全样本之最），却同时踩中三条红线（每文件 0.09 次提交、16 天内建成、此后再无更新）。按体量排名它会名列第一，按质量它一文不值。

## 三点警示：阅读任何 Harness 结论之前

**Harness 工程是一门新学科**。术语由 OpenAI 2026 年 2 月文章点燃，至今唯一的共识停留在「是什么」层面——**Agent = Model + Harness**（公式归功于 Birgitta Böckeler）。至于「如何可靠地构建」，仍是开放问题。清单中仓库的中位年龄仅 **8.7 个月**，没有任何团队拥有结构性领先。如果你还没有自己的 Harness，不必恐慌：145 个大型开源项目中只有 4 个声明了子智能体。

**Harness 工程是移动靶**。Harness 负责约束、引导并抬升模型，模型在变，Harness 的合理形态随之变化。2026 年初的好 Harness 对最新一代前沿模型已不再适用。Anthropic 给出了最干净的例证：他们曾为缓解模型的「上下文焦虑」加入上下文窗口重置机制，Opus 4.5 发布后该行为消失，为补偿而建的机制沦为死重。一般规律是：**Harness 编码了关于「模型做不到什么」的假设，而模型进步会让这些假设腐烂**。任何「好 Harness」的定义（包括本文）都注定快速过时。

**研究过程本身用了 AI**。作者借助 AI 收集、排序与聚合来源，否则工作量以周计。

## 数字里的 Harness 工程

**爆发式增长的领域**

| 指标 | 数值 |
|---|---|
| 携带 `claude-code` 话题的 GitHub 仓库 | 73,400 |
| 仅 2026 年新建的「agent harness」仓库 | 21,500 |
| Harness 仓库中位年龄 | 8.7 个月 |
| 创建于 2025 或 2026 年的占比 | 83% |

**人人写指令，几乎无人执行指令**

- 145 个大型开源项目中 **63%** 携带智能体指令文件，但只有 **4 个**声明子智能体，全部合计仅 **14 个 Hook**
- 根指令文件 **57%** 超过 100 行（OpenAI 自己收敛到的长度），中位数 **123 行**
- 391 个仓库中仅 **12 个**提交过一条 `deny` 规则；仅 **22 个**声明 `PreToolUse` Hook（可在动作执行前否决）
- 在使用子智能体的中位仓库里，只有 **1/4 的子智能体**拥有受限工具列表，其余能看到一切

**AGENTS.md 正在胜出**

- 189 个仓库在根目录放 `AGENTS.md`，155 个放 `CLAUDE.md`；大型开源项目的 53 个 `CLAUDE.md` 中 **36 个只是指向 AGENTS.md 的符号链接或短跳转**
- **46%** 的仓库为至少两种智能体（Claude Code、Codex、Copilot、Cursor、Gemini 等）编写指令

**鲜有 Harness 自我检验**

- 97 个体量足够测试的 Harness 中，**60% 既无测试也无 Eval**；21% 有测试，27% 版本化 Eval，两者兼备的仅 7 个

**智能体在编写自己的 Harness**

- 2025 年 1 月以来触及 Harness 的提交中，**25% 明确由 AI 署名**（这是下限，许多工具与人会抹掉签名）
- 在 79 个可比仓库中的 52 个里，Harness 的 AI 撰写比例高于它所治理的代码（中位数 16% 对 9%）

## 最佳实践一：测试并评估你的 Harness

与代码一样，Harness 也会藏 bug——过于冗长或含糊的指令时灵时不灵，`AGENTS.md` 里的规则可能从未被遵守。要确认 Harness 有效，必须测试。这仍是稀缺实践：六成的 Harness 只是无人知晓是否成立的 Markdown 指令。

测试与 Eval 是两份不同的工作，Harness 两者都需要。

**测试告诉你脚本仍然工作**。规则或 Hook 可能失效，测试是可复现的、用代码而非 LLM 完成的证明。测试有两种失败方式：放行了该拦的，或拦住了该放的。因此每条规则都要测两遍——确认该触发时触发、不该触发时不触发。Anthropic 一句话概括：*「对行为应发生与不应发生的情形都要测试。单边 Eval 造就单边优化。」* 若测试只含必拦项，收紧守卫永远安全、放松守卫永远不可见，Harness 会慢慢漂向「拦住一切」，把智能体勒死。

语料中最清晰的例子是 codex-claude-code-config：针对 12 个守卫归档 **63 个用例**——29 个必须拦截、19 个必须放行、15 个校验路由器发出的确切文本；`rm -rf /tmp/scratch-dir` 放行、`rm -rf /` 拦截，回放器对每个用例跑真实脚本。另一教训来自 flow-next：测试可能因触发条件从未命中而通过，也可能悄悄读到本机的个人配置。flow-next 故意埋了一个测试不该看到的文件，Harness 却「报告了全局属主拦截」——泄漏是真的，于是他们重写了设置加载方式。

**Eval 告诉你 Harness 有帮助**。冻结一组任务，端到端运行，给结果打分。对编码智能体而言，可以是一系列缺陷修复（带缺陷代码 + bug 报告），挑 20 到 50 个真实见过的失败，每个从干净状态出发且有已知正确答案。固定模型，一次只改 Harness 的一个部件，再逐一移除部件以辨别谁在真正出力。26 个含评估用例的仓库里，只有 flow-next 一家发布了带复现的前后对比，并坦然拥有自己的零结果。**如果你无法证明某条规则改善了智能体行为，就无法证明智能体需要它。**

## 最佳实践二：把 Harness 压缩到严格最小

从热门仓库下载技能、为安全研究加装专用子智能体，这些诱惑都应抵制。最新一代编码智能体开箱即用已相当强大，**Harness 应针对智能体的实际失败而构建，而非基于「它大概做不好」的假设**。

Harness 指令的最佳来源是过往会话：如果你曾纠正智能体，说明它缺少引导或控制，这值得一处增补。flow-next 公开实践了这一点：`.flow/memory/bug/` 下沉淀 **98 份 bug 复盘**，每份带 `root_cause` 字段与一段 `Prevention`，点名本该拦住它的规则。

作者还主张 **Harness 应由人来构建而非智能体**——如果智能体需要监督，它怎能决定自己需要怎样的监督？作者坦承这是观点而非发现：唯一的消融研究（NLAH）测得相反结论，自我改进的 Harness 在两个基准上分别提升 4.8 与 2.7 分。相关讨论可参见 [[AutoHarness|AutoHarness]] 与 [[Agentic-Harness-Engineering|智能体化 Harness 工程]] 的自动演化路线。

指令并非免费。ETH Zurich 在 138 个真实任务上测得：**机器生成的上下文文件反而拉低成功率**（相比完全不给上下文），推理成本还上涨 20% 以上；人写的文件约提升 4%。无论哪种，智能体都多烧 14% 到 22% 的推理 Token。OpenAI 试过单一巨型指令文件并点出四种死法：挤占真正的任务、*「当一切都很重要时，没有什么重要」*、*「瞬间腐烂……陈旧规则的坟场」*、*「一整块文本无法做机械检查」*。他们的替代品是约 100 行，主 AGENTS.md 只当规则树的目录。

工具同理。**智能体能看到的工具与技能数量是一个性能参数**，也是本次调研中极少数能同向移动成功率、Token 成本与延迟的旋钮。Vercel 从智能体中砍掉 80% 的工具，同一模型成功率从 80% 升到 100%，Token 减半，延迟从 724 秒降到 141 秒。微软的 Azure 运维智能体两周内工具数破百，最后不得不塌缩成两个宽泛工具。作者提醒：方向可信，幅度未经验证——Vercel 的数字标注为二手且无人复现。这也解释了为何没有仓库展示过这一实践：**克制在 git 里不留痕迹**。

## 最佳实践三：用脚本为规则兜底或直接替代规则

智能体可能遵守、也可能不遵守写在 `AGENTS.md`、Skill 或规则文件里的指令——Harness 规则越多，每次会话开头的上下文越是塞满（有时互相矛盾的）条文，遵守率越成问题。

研究者检查了 481 个公开 `CLAUDE.md` 文件中的书面安全规则有多少真实效力，结果在 **4% 到 16%** 之间震荡——对应的 Harness 形同失明。**用散文写下的规则几乎从未真正执行。**

最有效的 Harness 通过可执行守卫落实规则：git hook、linter 规则、静态分析、自定义脚本。这些检查既在运行 Harness 的机器上执行，也在 CI 中执行（并非每位开发者用同一套 Harness）。部分团队将检查接入智能体循环（通常经由 Hook），从而把书面指令压到最少。

差距不是装饰性的。codex-claude-code-config 的 `destructive-command-guard.py` 用正则拦下 `rm --recursive --force /`、`rm / --recursive --force` 与 `rm -rf /; echo done`——指望 LLM 凭文字描述识别这类模式，永远抓不全。

对抗幻觉的办法是让智能体引用脚本能校验的东西：**先由确定性代码生成原始事实**（涉及的文件与函数、改动触及的行），不带任何判断；智能体在事实之上推理；再由脚本把每条论断比对回去。一句话原则：**脚本负责度量、永不判断；智能体负责判断、永不度量。**

## 最佳实践四：让智能体自己运行应用

智能体写代码的速度已超过人类评审的速度，瓶颈不再是代码的生成，而是验证。可以把一部分验证下放给智能体：让它启动应用实例、在真实浏览器中打开、像真实用户一样点击界面、读日志定位 bug 与回归。

OpenAI 的实践：让每个工作副本可独立启动应用，把浏览器控制接入智能体运行时，并给每个工作副本配一套用完即弃的日志与指标栈供智能体查询。智能体复现 bug、记录失败、修复，再驱动应用演示修复成立。这还把书面指令变成了真正的检查：*「确保服务启动在 800ms 内完成」*、*「四条关键用户旅程中无任何 span 超过两秒」*。同一文章还描述了一个巧妙技巧：**把自定义检查的错误信息写成修复指南**——*「因为这些 lint 是自制的，我们把错误消息写成会向智能体上下文注入修复指令的形式」*。

智能体成功验证某个功能或修复后，应把验证沉淀为不依赖 LLM 的可复现脚本——冒烟测试，以降低 Token 成本与验证时间。测试 Harness 启动越快，智能体反馈环越短：确保测试应用一秒内启动，mock 掉不稳定的外部依赖。若想让多个智能体并行工作，改造应用使其能以多实例共存（不同端口与数据库 schema，最好是不同容器）。

## 最佳实践五：度量 Harness 的真实使用方式

Eval 告诉你某项改动在你挑选的任务集上是否有帮助，但无法告诉你真实会话中发生了什么：哪些技能真的触发了、Hook 拦下了多少次、不同工具配置下会话需要几轮迭代。这需要可观测性——像对待任何软件一样，度量 Harness 运行时实际发生的事。

VS Code 团队的做法：发布前跑离线基准，上线后持续度量——A/B 测试、聚合使用信号、周报。Anthropic 的 Eval 指南口径一致：生产监控能捕捉 Eval 错过的漂移，而且在有人亲自读过若干会话记录之前，不应相信任何 Eval 分数。

实现门槛并不高：Claude Code 可向任意 OpenTelemetry 后端写日志；n8n 加了一个在每次技能调用后触发的 Hook，把「技能已激活」事件发回自家遥测服务；claude-code-infrastructure-showcase 把每次技能建议、激活与拦截写入本地 `metrics.jsonl`，并附报表脚本（基准会话除外，避免污染数据）。

然而这仍是稀缺实践：**391 个仓库中只有 5 个**记录了 Harness 的使用情况。Atomic CRM Builder 记录每个会话的每一步，并让用户解析日志以理解技能与工具的使用模式。这与 [[Agentic-Harness-Engineering|可观测性驱动的 Harness 自动演化]] 的研究方向遥相呼应：没有使用数据，演化无从谈起。

## 最佳实践六：别让 Harness 腐烂

代码库演化很快，智能体参与后更快。某些架构变更会使某条规则失效；模型升级后，原本需要规则纠偏的行为可能已然做对。Harness 在某个时刻带来价值，价值却随时间衰减。

**多数控制措施的存在是为了补偿模型曾经犯过的错。模型不再犯时，控制就是纯成本。** 因此给每项控制写上过期条件，并记下它因哪起事故而存在。flow-next 维护了 9 份带日期、以所裁决事项命名的决策记录，外加一个 `declined/` 目录存放刻意不做的功能。作者自我批评：Atomic CRM 携带 148 个 Harness 文件与零份决策记录——没有任何文字说明每项控制为何存在，因而没有任何一项能被安全移除。

正确心态是把 Harness 当花园经营：定期扫描不再反映真实代码行为的陈旧文档，种新规则前先拔旧规则，每次重大变更后确认 Harness 依然工作。OpenAI 自动化了前半段：*「一个周期性的『文档园艺』智能体扫描不再反映真实代码行为的陈旧文档，并提交修复 PR。」* 另一个好习惯是扫描过往会话（Claude Code 的 JSONL 文件）寻找本该被 Harness 拦下的异常行为——一旦发现腐烂迹象，就是照料 Harness 的时刻，这项工作可部分委派给「园丁智能体」。

## 无效实践：失败尝试的教训

文献中同样宝贵的是失败记录。

| 做法 | 证据 | 结论 |
|---|---|---|
| 增设评审智能体 | NLAH 消融：基础智能体 41% 的任务成功率，加评审者后降 8 个百分点 | 代码反而变差；四角色团队 72.2% 对最佳单智能体 71.8%（SWE-bench 500），团队并无优势 |
| 超过 4 次智能体间交接 | 微软 Azure 运维智能体团队扩到 50+ 专家后回滚为少量通才 | *「需要四次以上交接的问题几乎总是失败」* |
| 事前写权限规则 | 113 名参与者对照实验：规则组比逐条审批组少拦 20.1 个百分点的危险动作 | 多数人把规则设成「问我」后照样批准（93% 的权限弹窗被批准）；**以弹窗收尾的规则不是规则** |
| 每次合并前等全部检查通过 | OpenAI 反向操作：少强制检查、短命 PR、 flaky 测试重跑而非卡合并 | *「纠正很便宜，等待很昂贵」*；但在低吞吐环境中同样做法不负责任 |
| 每轮循环丢弃上下文 | 「新鲜上下文」版 Ralph Wiggum 循环仅有一次无基线的玩具应用运行记录 | 循环本身有效（OpenAI 以 1500 个合并 PR 的规模运行）；真正有帮助的不是擦除上下文，而是**把工作写进文件** |

值得注意的自省：Atomic CRM 自己就有评审角色（作者称它确实常常改善结果），也串了 7 个角色，且仍要求每个 PR 人工评审——最佳实践清单并不必然等于作者自家仓库的现状，研究过程本身帮助他们厘清了既往的权衡。

## 作者的核心判断

通篇引用的强测量都来自**公共基准上的自主编码智能体**；而 Atomic CRM 这类 Harness 做的事不同——它在不受自己控制的任务上治理一个**流程**（独立工作副本、评审门禁、交付契约、合并纪律）。作者认为两种情形背后是同一机制：**围绕概率性步骤搭建确定性脚手架**。但这仍只是类比，唯有你自己的任务集能把类比变成测量——而那恰好是实践清单的第一条（测试并评估你的 Harness）。

作者同时呼吁：如果你的 Harness 与上述结论矛盾，请公开分享——那是从仓库里读不到的部分，开发者社区迫切需要来自真实场景的、有据可查的洞察，才能把这门学科推向前进。对刚入门的读者，可先读 [[What-Is-Harness-Engineering|什么是 Harness 工程]] 建立基础概念，再按 [[Harness-Engineering-Coding-Agents-Guide|编码智能体 Harness 构建指南]] 动手，规模化阶段参考 [[Agent-Harness-Platform-Playbook|智能体 Harness 平台手册]]。
