# 智能体 Harness 工程：2026 平台团队手册

本文基于 PuppyOne 发布的平台团队手册，从**平台治理**视角阐述智能体 Harness 工程的落地路径。与聚焦开发者体验的手册不同，本文面向接到「把智能体送上生产」任务的平台与基础设施团队，核心问题是：**怎样的控制平面能拦住第一次生产事故？**

> **核心论断**：Harness 工程的目标不是让智能体更聪明，而是让它**有边界、可归因、可验证、可回滚**。

## Harness 工程的本质定位

LLM 是无状态的预测器，生产级智能体是有状态的行动者。Harness 正是弥合两者鸿沟的治理层，负责五件事：

- 决定智能体**是谁**（身份）
- 决定它**能看见什么、能做什么**（策略）
- 校验它**即将改动什么**（验证）
- 记录**发生了什么**（审计）
- 在出错时给出干净的**回滚**路径

Builder.io 将 Harness 定义为「包裹 AI 模型、使其成为可用智能体的所有代码、配置与执行逻辑」；LangChain 的表述更精炼：**智能体 = 模型 + Harness**。Martin Fowler 则把 Harness 工程描述为构建「控制论调速器」（cybernetic governor）——行动前的**引导器**（guides）加上行动后的**传感器**（sensors）。这正是平台团队应有的心智模型：构建能在劣质 Prompt、不完整 Context 乃至对抗性输入下依然存活的控制机制。

### 与 Prompt 工程、Context 工程的分工

| 学科 | 改动对象 | 主要产物 | 缺失时的失效模式 |
| :--- | :--- | :--- | :--- |
| Prompt 工程 | 指令与约束 | 系统 Prompt 模板 | 智能体「听起来对」，但依然破坏工作流 |
| Context 工程 | 智能体可见的证据与状态 | 检索 + 状态打包 | 模型有能力，但盲目或不一致 |
| Harness 工程 | 治理与执行控制平面 | 身份 + 策略 + 门控 + 日志 | 智能体在规模化后变得不安全、不可靠 |

实践中，这类工作通常由**平台团队**承担——或是那个「突然变成了 Harness 平台团队」的平台团队。

## 五大原语：Harness 工程师必须拥有的不变量

将以下五项视为不变量：缺任何一项，手里的就不是 Harness，而是演示品。

### 1. 作用域身份（Scoped Identity）：按智能体划分，而非按人

身份是治理之根。Harness 必须对三个问题给出一等公民级别的答案：

- 当前行动的是哪个**智能体角色**？
- 它代表哪个**人**或哪个**工作流**？
- **作用域**多大、有效期多长？

最常见的失效是**身份坍缩**（identity collapse）：智能体借用用户会话、共享服务账号，或持有长期有效的密钥。WorkOS 归纳了三种反复出现的高危模式：借用用户会话、跨智能体共享服务账号、内置宽作用域静态 API Key。

> **警示**：如果 IAM 日志回答不了「是哪个智能体做的」，第一次事故复盘就过不了关。

**可扩展的工程模式**：

- **按智能体角色配置服务身份**（而非按人），把智能体当作工作负载对待
- **委托链**：用户 → 工作流 → 智能体身份，每一跳收窄作用域
- **短期令牌**用于工具调用，避免模型可读取的静态密钥——Aembit 指出，智能体可被 Prompt 注入「社会工程」诱导泄露环境变量中的密钥，静态凭证在结构上就是不安全的

### 2. 持久且智能体可读的状态

状态层必须同时满足三个属性：跨会话**持久**、**智能体可读**（结构化到足以驱动行动）、**人类可审查**。

多数团队会不小心落入三种陷阱之一：把所有东西堆进聊天历史直到溢出；把一切塞进向量数据库并祈祷检索「够用」；或干脆不存任何持久状态，反复重跑智能体直到「蒙对」。

正确的做法是把持久状态当作**接口**来设计：

- 权威的任务状态 Schema 是什么？
- 工件模型是什么？（计划、diff、结果）
- 检索契约是什么？（智能体能请求什么、会拿到什么）

**实用选型**：

- **文件（Markdown/JSON）**：人机都需检视并版本化变更时
- **数据库行**：需要事务约束、索引与跨系统联接时
- **混合**：数据库负责索引与权限，文件负责可审查工件

经验法则：**凡需要 diff、评审或回滚的状态，都以带版本的工件形式存储**。这与 WikiLLM 自身「LLM 维护全部 wiki 数据、人工编辑极少」的编纂原则同构。

### 3. 工具策略：白名单优于黑名单

工具策略是「智能体安全」落到实处的地方。黑名单假设你已知所有危险之事——事实并非如此。设计良好的 Harness 由三层构成：

- **工具注册表**（存在什么）
- **策略层**（该身份允许什么）
- **参数级约束**（哪些资源在作用域内）

Anthropic 的工具构建指南值得参照：把工具接口视为「智能体-计算机接口」（agent-computer interface），在命名清晰度、命名空间与高信噪比返回上持续投入。

**实用的策略模型**：

- 按智能体角色配置工具白名单
- 按调用限定资源作用域（路径、仓库、租户、目的地）
- 危险动词走审批门控（delete、deploy、rotate、bulk-modify）

### 4. 验证门控（Verification Gates）

验证区分了「模型说它做了」与「它确实安全地做了」。Harness 需要在两个位置设卡：

**行动前验证**（工具调用执行前）

- 策略检查：该身份是否获准使用此工具？
- 作用域检查：目标资源是否在范围内？
- Schema 校验：参数是否符合预期结构？
- 审批检查：是否属于特权操作？

**行动后验证**（执行之后）

- 工具返回是否符合预期？
- 状态变更是否与计划一致？
- 是否触犯了安全不变量？

OpenAI Agents SDK 支持工具级审批门控（`needs approval`）与动态工具启用（`is_enabled`）——这正是理想的形态：**权限在模型之外强制执行，而非在 Token 内部协商**。

**验证同时是安全边界**。Prompt 注入不是 Prompt 问题，而是治理问题。OWASP 将 Prompt 注入列为头号风险，建议纵深防御：最小权限、严格隔离不可信内容、输入/返回/行动三重筛查。对智能体系统而言，与 Harness 最相关的是**行动筛查**（action screening）：拿拟议的工具调用对照**用户原始意图**校验，而非对照检索文本里偷运进来的指令。

### 5. 审计 + 回滚：一个原语，不是两个

审计回答「发生了什么」，回滚回答「如何恢复」。二者必须作为一个原语对待——**无法回滚的日志只是事后验尸材料，而非运行期控制手段**。

**审计应记录**：

- 行动者身份（智能体角色 + 委托来源）
- 工具调用意图与参数（必要时脱敏）
- 策略裁决（放行/拒绝 + 理由）
- 执行结果
- 状态增量（改了什么）

**回滚需要具备**：

- 带版本的工件
- 可 diff 的状态迁移
- 不依赖「让智能体自己撤销」的恢复机制

微软的 Event Sourcing 模式阐明了追加式事件存储的核心价值：提供审计轨迹，并允许通过重放重建状态。即便不实现完整的事件溯源，原则依然成立：**追加式历史 + 可复现重建**是底线。最简可用版本则可参照 Martin Fowler 经典的 Audit Log 模式。

## 框架 ≠ Harness：工程级辨析

团队最常卡住的地方，是买了一个框架就宣布有了 Harness。运维意义上的分野如下：

| 维度 | 框架（Framework） | Harness |
| :--- | :--- | :--- |
| 主要产物 | 图/DAG、智能体循环、工具抽象 | 身份 + 策略 + 验证 + 审计轨迹 |
| 归属方 | 应用团队 | 平台 + 安全团队 |
| 替换成本 | 高（深嵌应用代码） | 应当低（智能体必须可替换） |
| 优化目标 | 开发者人体工学 | 治理与可存活性 |
| 典型失效 | 演示可用，生产漂移 | 应当阻断或回滚不安全动作 |

一句话：**图是编排，Harness 是治理。** LangChain/LangGraph 适合用来组装智能体，但不要把它误认为治理层。

## 平台落地路线：30/60/90 天

### 第 0–30 天：最小可行 Harness

目标不是自治，而是**有证据的受限执行**。交付四件事：

1. 按智能体角色的服务身份（作用域暂时宽松也可接受）
2. 一个存放工件与任务状态的持久状态库
3. 记录工具调用与状态变更的追加式审计日志
4. 人工回滚 Runbook（人可从已知良好状态恢复）

**完成判据**：每一次工具调用都能回答「谁做了什么」；无需请求模型撤销即可回退一次错误写入。

### 第 31–60 天：策略 + 验证

收紧闭环：

- 按角色的工具白名单
- 参数级作用域（路径/租户/仓库）
- 工具调用的 Schema 校验
- 特权动词的审批门
- 最小评估 Harness：智能体能否在不违反策略的前提下走完黄金路径？

以 Anthropic「构建高效智能体」的建议为标尺：沙箱中测试、保持工具整洁、令系统可观测。

### 第 61–90 天：跨团队平台化

此时构建的是平台，而非单个智能体：

- 策略注册表（带版本的策略）
- 标准化「智能体入职」模板（身份 + 默认工具集）
- 共享可观测性仪表盘（成本、延迟、失败原因）
- 事故演练（Prompt 注入、越界工具调用、回滚测试）

## 反模式清单（上线前自查）

1. **跨智能体共享「上帝令牌」**：一把钥匙无所不能，终将无所不用
2. **默认挂载全部工具**：工具墙不会让智能体更强，只会让它更难约束
3. **无追踪的工具写入**：写入不记日志、不做 diff，缓慢漂移要等用户投诉才会暴露
4. **Prompt 注入爆炸半径**：不可信内容若能在无行动筛查的情况下影响工具调用，等于把控制信道拱手让给攻击者
5. **评估事后补票**：说不清「完成」的定义，智能体不是提前收工就是无限循环
6. **「Harness == LangGraph」误解**：见上节，编排不等于治理

## 自建还是采购

**自建**的条件：已有可复用的 IAM/策略基础设施；需要深度定制集成并追求完全掌控；能把 Harness 当作平台产品投入人力（而非副业项目）。

**采购/采纳现成 Harness 层**的信号：多个团队立刻需要一致的策略与审计；正在经受安全/合规评审；智能体需要共享、受治理且可回滚的状态。

一个简洁的决策问题：**若智能体可以改动生产状态，你是否已有可强制执行的审批 + 审计 + 回滚控制平面？** 若没有，那就是你要建（或买）的东西。
